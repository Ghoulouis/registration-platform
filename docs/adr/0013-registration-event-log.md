# Registration Event Log: two-bucket result, level carries severity, console-only for now

The Server had no logging at all for REGISTER/RENEW/CANCEL outcomes — no way to see success rates or detect suspicious activity (repeated bad signatures) without reading Client-side console output one Simulated Client at a time. We added a structured log line per completed REGISTER/RENEW/CANCEL attempt, on both Server and Client, carrying Client ID, transaction (REGISTER/RENEW/CANCEL), event type (the specific outcome, e.g. `invalid_token`), and result.

**Placement**: the Server logs from `TcpServer.handleWithTraceContext`, not `RegistrationService` — it already sits at the boundary between wire-level request/response and business logic (it's also where Trace Context, ADR-0012, is scoped via MDC), so it can classify outcomes generically from `(request, response)` pairs without `RegistrationService` needing any logging concern at all. A dedicated `RegistrationEventLog` class owns the classification so it's unit-testable independent of the reactor.

**Result has two values, not one per status**: `SUCCESS` or `REJECTED`. `ALREADY_REGISTERED`, `NOT_REGISTERED`, `CHALLENGE_REJECTED`, and `INVALID_TOKEN` are all `REJECTED` — the request wasn't honored, regardless of why. What distinguishes a benign retry (`ALREADY_REGISTERED`, `NOT_REGISTERED` — usually a Client's own earlier attempt landing, ADR-0005) from a real signal worth alerting on (`CHALLENGE_REJECTED`, `INVALID_TOKEN` — a wrong signature, possibly an attacker probing a guessed Client ID) is the **log level**, not a third result bucket: WARN for the two signature-rejection cases, DEBUG for the two benign-retry cases, INFO for genuine `SUCCESS`. Splitting severity into the result field instead would have made `result` do two jobs at once (what happened, and how urgent it is) for no benefit — the level already exists for exactly this purpose.

REGISTER's Step 1 (issuing a pending Nonce) is not logged as an event — it's not a completed transaction, just routine, high-volume, mid-flow traffic every REGISTER attempt produces regardless of outcome.

**Console only for now.** MDC already carries Trace Context (ADR-0012), and the default Logback console pattern doesn't render MDC values — confirmed by a live test where they were set correctly but invisible in output. Rather than block this on choosing a shipping mechanism (a Logback JSON encoder plus an external agent like Filebeat, versus the app calling Elasticsearch directly), the new fields are written directly into the log message text so they're immediately readable now. Wiring a JSON encoder and deciding the shipping mechanism is deferred; when it happens, these fields can move into MDC or an SLF4J 2.x structured key-value call without changing where the log statements live.
