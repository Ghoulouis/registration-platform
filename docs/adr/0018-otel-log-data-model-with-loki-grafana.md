# OpenTelemetry Log Data Model logging, shipped to Loki via a Collector

Server and Client logs (ADR-0013/0014, ADR-0012) have been console-only text, not yet shipped anywhere queryable. We adopted the real OpenTelemetry Java SDK (`opentelemetry-sdk`, `opentelemetry-logback-appender-1.0`, OTLP gRPC exporter) rather than a lightweight JSON encoder that merely mimics the Log Data Model's field names: this gives genuine `Timestamp`/`SeverityNumber`/`Body`/`Attributes`/`Resource` semantics and a real path to OTLP export, at the cost of pulling in the SDK and a collector dependency. Every log line (framework and business) goes through one appender addition — `RegistrationEventLog`'s business fields (Client ID, transaction, event type, result) are emitted as structured Attributes rather than baked into the message string, so they're queryable independently. It's moved into a new shared `common.observability.RegistrationEventLog` so Server and Client emit identically-shaped events instead of Client's existing ad hoc log calls drifting from Server's structure. The existing plain-text console appender is kept alongside the new one — local dev still reads the terminal directly.

Trace correlation reuses ADR-0012's existing Trace ID/Span ID rather than adopting a full OTel Tracer: at the same points that populate MDC today (`TcpServer`, `RetryingRequester`), the existing 16/8-byte IDs are wrapped as a real `Span.wrap(SpanContext...)` and made the current `Context`, so the Log Data Model's `trace_id`/`span_id` fields populate via the SDK's normal mechanism. No spans are ever recorded or exported — this is log correlation only, not distributed tracing.

Logs export via real OTLP (gRPC) to an OpenTelemetry Collector, which forwards to Loki; Grafana visualizes it with a pre-provisioned Loki datasource. All three are one new `compose.logging.yml`, replacing the previously-unwired `compose.collector.yml` and the now-deleted `compose.elasticsearch.yml` (Elasticsearch/Kibana were scaffolded for this same "make logs queryable" need but never wired up; Loki/Grafana was chosen instead once the choice became concrete). Only `service.name`, `severity`, and `transaction` are configured as Loki labels; `clientId`, `eventType`, and `result` stay in the log body/structured metadata — Loki indexes labels as separate streams, and Client ID's up-to-1-million cardinality (CONTEXT.md's target scale) would explode the index if it were one.
