# Step-level Registration Event Log lives inside RegistrationService

ADR-0013 deliberately placed the Registration Event Log at the `TcpServer` boundary, classifying each `(request, response)` pair after `RegistrationService.handle()` returned, specifically so `RegistrationService` stayed free of any logging concern. That worked for one line per completed transaction, but not for step-level logging — "a Nonce was issued," "auth data was received," "the signature verified," "the store was updated" are all steps `RegistrationService` passes through on the way to a response; a wrapper that only sees the final `(request, response)` pair structurally cannot see them. There's no way to get this granularity without putting logging where the steps actually happen.

We moved logging into `RegistrationService` itself, at each decision point, accepting the loss of the clean separation ADR-0013 established. `RegistrationEventLog` now offers two calls: `step(clientId, transaction, eventType)` — always DEBUG, no result, for the intermediate/informational events — and `outcome(clientId, transaction, eventType, result, level)` — the existing terminal-event shape, unchanged in meaning (result is `SUCCESS`/`REJECTED`, severity is the log level, not a third result value). `TcpServer` no longer classifies anything; it's back to only wiring Trace Context (ADR-0012) into MDC around the call.

The Client side mirrors this: `RetryingRequester.attemptRegister` — the one place that actually performs Register's two legs — logs `requesting_nonce` before Step 1 and `submitting_auth_data` before Step 2, for the same reason: that granularity doesn't exist anywhere else in the call chain.

Distinguishing *why* a Nonce was rejected — expired vs. already consumed (a replay) vs. a genuinely wrong signature — was considered and explicitly deferred: `RegistrationStore.get()` deliberately collapses "never existed," "expired," and "already consumed" into a single absent-record signal (ADR-0011), and telling them apart would mean the store keeping reasons around instead of just discarding stale state — a real store-level change, not a logging one. For now, these all log as one generic rejection event using whatever `RegistrationService` can already see. Wire responses are unaffected either way — the Client never sees more detail than `CHALLENGE_REJECTED`/`INVALID_TOKEN` already gave it; the added granularity is Server-log-only, so a caller (legitimate or not) never learns *why* a rejection happened, only that it did.
