# Virtual threads + striped ReentrantLock replace the NIO Selector (Centralized Server only)

ADR-0001's single-threaded NIO Selector reactor was never actually solving an async-I/O problem here — `RegistrationService` is backed by an in-memory store with nothing to await, so it was chosen mainly to keep the Centralized Server's shape consistent with the Distributed Server's. Its real cost: every REGISTER/RENEW/CANCEL, for every Client, is serialized through one thread, leaving every other CPU core idle regardless of how many independent Clients are calling in at once.

We replaced it with one virtual thread per connection, doing plain blocking I/O — the same style `TcpClient` already uses (ADR-0006). This is scoped to the `server` module only; `server-distribute` is untouched. Different Client IDs now genuinely run in parallel across cores; the code also reads like straight-line blocking I/O instead of a callback-driven reactor.

Going single-threaded to multi-threaded reintroduces a class of bug the reactor used to rule out for free: several sequences in `RegistrationService` are check-then-act (read the store, decide, then write) rather than a single atomic store operation. Two requests for the *same* Client ID overlapping in time can now genuinely race. We serialize per Client ID with a lock, scoped to exactly `RegistrationService.handle(...)` — never around the socket read/write (locking around blocking I/O would stall every other request for that Client ID for no reason), and never held across Register's two legs (Step 1 and Step 2 are separate connections on separate virtual threads at genuinely different times; nothing needs to bridge that gap since the pending-Nonce state in the store already carries it, exactly as it did under the single-threaded reactor).

The lock is a `ReentrantLock`, not `synchronized`. This project targets Java 21, not 24 — JEP 491 (fixing virtual threads pinning their carrier while blocked entering a `synchronized` block) isn't available yet. `ReentrantLock` doesn't have that problem and is the JDK team's own recommended primitive for virtual threads.

Locks are a fixed pool of 256, chosen by hashing the Client ID (`StripedLock`) — not an unbounded `Map<ClientId, Lock>`. CONTEXT.md's stated target is up to a million Clients on a long-running process; an unbounded per-Client-ID map would grow forever, since nothing ever removes an entry once a Client cancels or expires. Different Client IDs occasionally sharing a stripe is harmless — each Client has at most one request in flight at a time in practice, so real contention on a shared stripe is rare.

The Store's own operations (`computeIfPresent`, `remove`) were already atomic at the map level and `RegistrationService` already handles the "lost the race" case (a `computeIfPresent` that finds nothing there) for the confirm/rotate paths — both needed regardless of this change, since the periodic reaper (ADR-0007) was already running concurrently with request handling even under the single-threaded reactor. No changes were needed there.
