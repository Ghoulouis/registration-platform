# Unify Challenge into Nonce; one record per Client ID

ADR-0009 deliberately split Challenge (pre-Registration, single-use, no retry tolerance) from Nonce (post-Registration, rotates, one-generation retry grace) into separate types and separate stores, reasoning that they occupy mutually exclusive lifecycle phases. That reasoning about the *retry policies* still holds — but it turned out not to require separate *types* or *storage* to enforce.

Both are structurally identical: a 32-byte random value, signed with the same Shared Signing Key, verified the same way. The only real difference is which policy applies, and that's a property of whether the Client ID currently has a confirmed Registration — a single boolean, not a reason to duplicate the value type or split the storage into two maps keyed by the same `ClientId`.

We merged `Challenge`/`ChallengeResponse` into `Nonce`/`NonceSignature` everywhere (wire protocol, `Ed25519` utility, server storage), and merged `ChallengeStore` into `RegistrationStore` as one record per Client ID with a `registered` flag: `false` (PENDING — a Nonce was issued for an unconfirmed Register attempt) or `true` (CONFIRMED — a live Registration). Deliberately, `registered` answers *which phase*, not *is this currently live* — liveness is still always a fresh comparison against an expiry timestamp (`nonceExpiresAt` while PENDING, the Registration's own `expiresAt` while CONFIRMED), checked eagerly on every read (`RegistrationStore.get`), never dependent on the reaper's timing. Collapsing that into the boolean would have reintroduced exactly the kind of staleness bug the original store design was careful to avoid: a record could sit with `registered=true` after its Registration had actually lapsed, if nothing happened to proactively flip it before the reaper next ran.

The two retry policies (Register: restart from scratch on any failure; Renew/Cancel: one generation of grace) are unchanged in substance — they still branch on the same PENDING/CONFIRMED distinction, just read from one field instead of implied by which store/type a value came from. The wire bytes are unaffected: a Challenge and a Nonce were always the same 32 bytes, so this is a Java-level and storage-level consolidation, not a protocol change.
