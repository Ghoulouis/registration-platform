# W3C Trace Context for request correlation, carried on Requests only

Register's two-step exchange (ADR-0009) runs over two separate TCP connections, and `RetryingRequester` retries any of REGISTER/RENEW/CANCEL over further separate connections on timeout. There was no way to link the resulting log lines back into one logical operation short of guessing from Client ID plus rough timing.

We adopted the [W3C Trace Context](https://www.w3.org/TR/trace-context/) `traceparent` shape (`version-trace_id-parent_id-trace_flags`) rather than a bespoke correlation ID, so that if these logs are later fed into Elastic APM, Jaeger, or any OpenTelemetry-speaking backend, they're understood natively — no bespoke Kibana query needed to reconstruct correlation. We only carry the core `traceparent` fields, not `tracestate`: this is a two-party system (Client and Server, no further downstream hops), so there's no multi-vendor propagation need `tracestate` exists for.

Fields are transmitted as raw bytes (26 bytes: 1-byte version + 16-byte trace ID + 8-byte span ID + 1-byte flags) rather than the 55-character ASCII form used in HTTP headers, consistent with this protocol's existing binary-over-text choice (ADR-0003). The standard hex-string form is used only when logging.

**Trace ID** scope matches one logical operation as `RetryingRequester` sees it: generated once per `register()`/`renew()`/`send()` call, shared across every retry and, for Register, both of its two legs. **Span ID** is regenerated by the Client for every individual connection attempt within that Trace — each retry, each Register leg gets its own. The Server logs using the Span ID it received rather than minting its own child span: proper distributed tracing has each hop create a child span, but that model earns its complexity when there are further hops to distinguish, and there aren't any here — adding a Server-side child span would be one more ID to manage without reflecting any real additional structure in the trace. `trace_flags` is always `0x01` (sampled); there's no sampling logic yet to make it meaningful otherwise.

Only `RegisterRequest`/`RenewRequest`/`CancelRequest` carry the Trace Context on the wire. Responses don't need to echo it back — the Server already has the Trace ID and Span ID in hand from the Request it just processed, at the point where it logs the outcome.
