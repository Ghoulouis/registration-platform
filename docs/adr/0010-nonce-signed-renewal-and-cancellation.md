# Nonce-signed Renewal and Cancellation, with one generation of rotation grace

`RenewRequest`/`CancelRequest` were both a bare Client ID with zero proof of identity — anyone who could guess or observe a 12-digit Client ID could renew or cancel someone else's Registration. Register already proves identity via an Ed25519 signature (ADR-0009); Renewal and Cancellation needed the same guarantee.

We considered a bearer Session Token (Server issues an opaque value, Client just presents it back) before settling on reusing the **same Ed25519 mechanism as Register**: the Server holds a Nonce for each live Registration, and the Client must submit a Nonce Signature (a signature over that Nonce, using the same Shared Signing Key already used for Register) to Renew or Cancel. This was chosen over a bearer token because it never puts a usable secret on the wire — only a signature, which is worthless without the private key — so there's no leak risk in ever handing the current Nonce back to an unproven caller. The Nonce itself is not secret; only the ability to sign it proves anything.

The Nonce is issued fresh (unrelated to the just-consumed Challenge) when Register succeeds, and **rotates on every successful Renewal**: the Server verifies the submitted signature, generates a new Nonce, stores it, and returns it in the success response for the Client to use next time. Cancellation verifies the same way but doesn't rotate — the record is deleted.

Rotation on every Renewal creates a lost-response hazard specific to this system's short-lived-connection-per-call model (`TcpClient`: connect, send, read one response, close — no delivery guarantee, and `RetryingRequester` already retries on timeout): if the Server rotates and responds, but the response is lost, the Client only ever knew the *old* Nonce and would otherwise be permanently locked out of Renewing again. We close this by keeping **one generation of rotation grace**: the Server remembers `previous Nonce -> current Nonce`. A Renewal signed with the previous Nonce is treated as the Client's own retry landing twice — it gets back the *same* current Nonce, unchanged, rather than being rejected or rotated again. Critically, a grace hit does not advance `previous`/`current` further, so this survives any number of consecutive lost responses, not just one.

A signature that matches neither the current nor the previous Nonce is a real failure: the response is `INVALID_TOKEN`, carrying the actual current Nonce (harmless to disclose, per the "Nonce isn't secret" reasoning above) so a sufficiently out-of-sync Client can resynchronize and retry with a correctly-signed follow-up, rather than being forced to fully re-Register. `INVALID_TOKEN` is deliberately a separate status from `NOT_REGISTERED` — the latter already has a retry-safety rule (a retried Register/Renew/Cancel treating `ALREADY_REGISTERED`/`NOT_REGISTERED` as success, ADR-0005) that would be actively wrong to apply to a wrong-signature rejection.

Cancellation needs no equivalent grace: deleting a Registration is a terminal, all-or-nothing mutation, and ADR-0005's existing "retried `NOT_REGISTERED` is success" rule already makes a retried Cancel-after-a-lost-response safe — once the record is gone, there's nothing left to check a signature against, and the right answer is unconditionally `NOT_REGISTERED`.
