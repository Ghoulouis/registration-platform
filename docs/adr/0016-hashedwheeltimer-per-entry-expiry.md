# HashedWheelTimer replaces the periodic full-sweep reaper (Centralized Server only)

`InMemoryRegistrationStore.reapExpired()` (ADR-0007) evicts lapsed entries by scanning the entire `recordsByClientId` map on every `registration.reaper-interval-millis` tick (1000ms by default). At CONTEXT.md's target of up to a million Clients, that's O(n) work running repeatedly on Spring's scheduler thread, competing for CPU with the request-handling virtual threads ADR-0015 introduced. We replaced full periodic scanning with per-record expiry scheduling: each write (`issuePendingNonce`'s Nonce TTL, `confirm`/`rotateNonce`'s Validity Period) schedules its own `io.netty.util.HashedWheelTimer` timeout instead of waiting for the next sweep to find it.

This is a deliberate dependency addition, not a free one. ADR-0015 moved the Centralized Server off a reactor/Netty-style model specifically to get plain, straight-line blocking code; this reintroduces one Netty utility class (`netty-common` only — no transport or handler code) purely for its O(1) amortized timer-wheel scheduling. We considered a dependency-free alternative — a `DelayQueue`/`PriorityBlockingQueue` drained by a dedicated thread, giving O(log n) schedule/cancel — but per-record scheduling churns proportionally to Register/Renew/Cancel traffic, which at a million Clients is exactly the high-timer-churn regime `HashedWheelTimer` was built for (it originates from Netty's own per-connection I/O timeout handling).

Moving from periodic-sweep to per-record timers reintroduces a race the sweep never had: a superseded timer (e.g. a pending Nonce's timeout, still queued, firing just after that Nonce was confirmed) must not evict the newer state it no longer corresponds to. Eviction is therefore a compare-and-remove — `recordsByClientId.remove(clientId, capturedRecord)`, using the exact `Record` instance captured when that timeout was scheduled — so a stale firing silently no-ops instead of deleting live state, the same atomicity style `computeIfPresent` already uses elsewhere in this class. Superseded timeouts are also actively cancelled on every write, tracked via a second `Map<ClientId, Timeout>` rather than a field on `Record` itself (keeping `Record` a plain immutable value, with no Netty type in it, and avoiding having to obtain a `Timeout` handle before the `Record` that needs to reference it exists) — but that cancellation is best-effort housekeeping, not what makes this correct; the compare-and-remove is the actual backstop.

That second map has the same unbounded-growth risk ADR-0015 called out for an unbounded `Map<ClientId, Lock>`: every distinct Client ID that ever registers would otherwise leave a permanent entry. `remove()` (Cancellation, and discarding an invalid pending-Nonce attempt) clears its entry, and the timer's own eviction callback clears its own entry too — also as a compare-and-remove (`timeoutsByClientId.remove(clientId, thisTimeout)`), so an old firing can't delete a newer timeout that has already replaced it there.

`reapExpired()` stays, at a much lower frequency, as a defense-in-depth safety net — consistent with `get()`'s existing eager `isExpired()` check, correctness here has never depended on any single timing mechanism. Without it, a stalled or misbehaving timer thread would leak any entry whose Client never calls in again, which is precisely the scenario Expiration (ADR-0007) exists to handle.
